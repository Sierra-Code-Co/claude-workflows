# SC-008 — a locally modified vendored file is named distinctly

**Verified 2026-08-16 by modifying a real vendored file, not by reasoning.**

## Method

Appended one HTML comment to `.claude/skills/speckit-clarify/SKILL.md`, ran
`scripts/speckit_drift.py`, restored the file, and re-ran.

## Result

| state | exit | report |
|---|---|---|
| modified | **1** | `[MODIFIED] … WILL OVERWRITE them` naming `.claude/skills/speckit-clarify/SKILL.md` |
| restored | **0** | `Every vendored file matches the manifest` |

`git status --porcelain` on the probe file afterwards: **0 lines** — the probe
left nothing behind.

The two states are distinguishable by exit code AND by named path, which is
SC-008's requirement. The report also states the CONSEQUENCE ("will overwrite"),
because "differs from the manifest" does not tell a reader their edit is about
to be destroyed.

## What the audit changed about the feature

Three things this exercise surfaced that reasoning had not:

1. **The shipped manifest tracked 1 file of 23** and reported no drift. Coverage
   was 4% and the output was indistinguishable from full coverage. Now 22 files,
   with `untracked` counting against clean so the state cannot recur silently.

2. **Provenance decides what counts as vendored.** `review-plan-v2/SKILL.md` has
   no `source:` frontmatter — it is ours, `specify init` will never touch it,
   and reporting it as at-risk would be false. Nine skills carry
   `source: templates/commands/*.md` and genuinely are at risk. A report that
   cries wolf on a file nobody will overwrite is one people stop reading, which
   costs the nine real ones.

3. **Rebuilding the manifest from disk baselines whatever is there.** Git
   history shows `.specify/templates/plan-template.md` has 2 commits since its
   initial add — a deliberate local edit. The rebuild recorded that edit as
   "pristine", so the file most at risk went quiet. `local_edits` now records
   the human judgement that hashing destroyed, and a rebuild carries it forward
   rather than recomputing it.

The first draft of the report then CONTRADICTED itself — printing "an update
will not clobber local work" directly beneath a banner saying one file would be
clobbered. The summary is narrowed when local edits exist; a report that argues
with itself is worse than a terse one.

## Related: T055, the workflow that could not fail

`check-speckit-update.yml` resolved both the installed and upstream versions
with `|| echo "unknown"`. On any API failure both became `"unknown"`, compared
**equal**, produced `needs_update=false`, and the job went green — a drift check
reporting "you are up to date" from a lookup that never happened. Both lookups
now fail the run with an explicit message saying the run checked NOTHING.
